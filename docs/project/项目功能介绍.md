# openGym 二次开发技术方案：从开源项目到 AI 健身 SaaS

> 整理日期：2026-10-14  
> 来源：ChatGPT 对话《项目功能介绍》中的最新技术方案。本文保留对话中的方案与调研结论；上游版本、源码细节及授权信息未在本次文档生成时重新核验。


**项目定位：先打造一个能展示全栈开发和 AI 工程能力的作品，再通过真实用户验证 C 端商业模式，后续考虑健身房及私教业务。**

我已经进一步查看了 openGym 的前后端代码结构、API 文档、AI Coach、数据同步机制、自动化测试以及开源许可证。

有几个重要发现，会直接影响我们的开发方案。

## 一、源码分析后的关键结论

### 1. openGym 的完成度比一般开源健身项目高

截至 2026 年 10 月 14 日，仓库最新正式 Release 是 **v1.4.1**，发布于 10 月 10 日。

目前代码已经具备：

- React H5 / PWA 和移动端适配。
- 训练计划、训练日志、肌肉分析和力量趋势。
- 5,600 多个健身动作及演示。
- 多用户账户及 Passkey 登录。
- 密码登录、设备配对和离线数据同步。
- AI Coach、训练回顾和计划调整。
- 支持多家模型提供商的 AI 接口。
- MCP 只读训练数据访问。
- 自动化测试与 Docker 部署。

**这意味着，我们不需要重新开发一个健身管理系统。**

更重要的是，项目已经有简体中文和繁体中文语言文件，因此也不需要从零开发中文国际化。

对应源码：

- [前端代码](https://github.com/DuarteSantos8/openGym/tree/main/frontend)
- [后端代码](https://github.com/DuarteSantos8/openGym/tree/main/api)
- [中文语言文件](https://github.com/DuarteSantos8/openGym/blob/main/frontend/src/locales/zh.js)
- [最新 Release](https://github.com/DuarteSantos8/openGym/releases/latest)

### 2. AI Coach 已经实现，不能把它当作我们的核心创新

这个发现尤其重要。

现有 AI Coach 不只是简单地调用 ChatGPT。

它已经支持：

- 根据健身目标生成训练计划。
- 根据训练记录回顾训练表现。
- 分析单次训练并给出建议。
- 使用自然语言修改训练计划。
- 在用户确认后应用 AI 建议。
- 对模型生成的修改执行结构化验证。

例如，项目中的：

`api/coach/core/validate.js`

负责校验 AI 提出的训练计划修改是否符合允许的操作和动作数据约束。

因此，假如我们只是给系统增加一个聊天机器人，再让它分析健身数据，**商业竞争力可能非常有限**。

我建议将差异化方向调整为：

**更易用的训练记录 + 可量化的训练进步分析 + 可解释的个性化建议。**

也就是说，AI 是产品的一部分，但不是产品的全部。

### 3. 项目适合技术作品，但尚不能直接视为成熟的商业 SaaS

目前 openGym 的核心设计目标仍然是：

> 用户自己部署，自己管理数据。

而商业 SaaS 的目标是：

> 用户只需要注册账号，平台负责存储、同步、可用性、安全和服务运营。

两者有明显区别。

例如现有系统使用 JSON 文件保存用户数据，而不是关系型数据库。它可以管理多个用户，但不代表已经满足规模化 SaaS 对高并发、备份恢复、运营和数据治理的全部要求。

所以，我们的任务不只是二次开发功能，还需要逐步完善产品化基础设施。

## 二、哪些功能复用，哪些功能自己开发？

这是第一版的功能边界。

| 功能 | 源码位置 | 我们的处理方式 |
|---|---|---|
| 训练计划与动作管理 | `frontend/src/views/Plan.jsx` | 直接复用 |
| 单次训练记录 | `frontend/src/views/Workout.jsx` | 复用，优化移动端交互 |
| 训练历史 | `frontend/src/views/History.jsx` | 直接复用 |
| 力量与训练统计 | `frontend/src/views/Stats.jsx` | 复用并增加分析指标 |
| 肌肉分布图 | `frontend/src/components/BodyMap.jsx` | 直接复用 |
| 用户登录 | `api/server.js` | 初期复用，后期完善 |
| 数据同步 | `frontend/src/store/useStore.js` | 保留现有机制 |
| AI Coach | `api/coach/` | 复用基础能力，扩展解释性分析 |
| AI 数据访问 | `api/coach/core/payload.js` | 研究后扩展，保留隐私边界 |
| SaaS 用户运营 | 现有功能不完整 | 后续新增 |
| 订阅与计费 | 不属于现有核心系统 | 商业验证后新增 |

### 我建议第一版新增三个功能

**功能 A：训练数据分析增强**

让用户了解自己过去 7 天、30 天的训练情况，包括：

- 每周训练次数。
- 各肌群训练组数与变化。
- 主要动作的重量、次数趋势。
- 训练计划完成率。
- 可能的训练停滞迹象。

其中，训练停滞应结合多个指标判断，不能仅凭一次重量下降就认定退步。

**功能 B：有数据依据的 AI 周报**

相比普通 AI 聊天，我更看重分析结果的可解释性。

例如：

> 过去四周，你的坐姿划船训练重量从 50 磅增加到 60 磅。
>
> 最近两次训练没有继续增加重量。
>
> 建议下次优先尝试完成既定次数，而不是立即继续加重。

报告应展示所依据的训练记录，让用户能够核对。

不过，**openGym 已有训练回顾能力**，因此周报不能只是把它换一种文字形式。我们的新增价值应是持续的数据对比、指标解释、报告留存和反馈闭环。

**功能 C：训练建议反馈**

用户可以标记：

- 建议有用。
- 建议不适合。
- 实际采用了建议。
- 下次训练后效果如何。

这些反馈可以帮助我们评估 AI 建议的实用性，而不只是统计 AI 调用了多少次。

## 三、技术架构：暂时不重写 Node.js

这里我会调整之前的建议。

**第一版不建议直接采用 React + Node.js + FastAPI + PostgreSQL 四层架构。**

不是这个架构不能做，而是当前项目没有必要一开始就引入两套后端和两套数据存储。

它会增加以下工作：

- 两套后端如何识别同一个用户。
- 用户退出登录后如何撤销访问权限。
- 如何保持分析数据与训练数据一致。
- 两个服务如何部署、监控和排查故障。
- 修改训练记录后如何更新统计结果。

对你目前的目标来说，这些工作会拖慢第一次产品交付。

### 推荐采用渐进式架构

**第一阶段：先使用原项目架构。**

```text
                  iPhone / Android / PC
                            │
                       H5 / PWA
                            │
                       React 19
                            │
                         Nginx
                            │
                      Node.js API
                            │
                ┌───────────┴──────────┐
                │                      │
             JSON 数据               AI Coach
                │                      │
           用户训练记录             模型 API
```

先把一个端到端功能开发完成。

**第二阶段：增加独立的数据分析服务。**

```text
                  React H5 / PWA
                         │
                       Nginx
                         │
                     Node.js API
                         │
             ┌───────────┴───────────┐
             │                       │
        原有业务 API            新增分析接口
             │                       │
       用户训练记录             FastAPI 服务
             │                       │
         JSON 文件          ┌────────┴────────┐
                            │                 │
                       PostgreSQL         AI API
                            │
                       分析结果存储
```

这里的 PostgreSQL 最初只保存新增业务数据和分析结果。

**训练记录仍以 openGym 原有数据为准。**

FastAPI 应通过受保护的内部接口获取当前用户的训练数据快照，不能直接相信浏览器传入的用户 ID。

Node.js 验证用户身份后，向内部服务传递经过服务端校验的用户标识和数据。服务之间使用专门的鉴权机制，并且不将 FastAPI 的内部接口直接暴露到公网。

后续可以使用 PostgreSQL 保存：

| 数据表 | 作用 |
|---|---|
| `analysis_profiles` | 分析用户与原系统用户的映射 |
| `workout_snapshots` | 用于分析的训练数据快照 |
| `training_metrics` | 计算后的训练指标 |
| `ai_reports` | AI 历史分析报告 |
| `ai_usage` | AI 调用量、模型消耗与费用 |
| `user_feedback` | 用户对建议的反馈 |

为了避免出现两份互相冲突的训练记录，快照需要记录来源修订号，并支持幂等更新。

这样的架构既能够保留开源项目，又可以让你重点练习 FastAPI、PostgreSQL、API 设计和异步任务。

### 为什么现在不直接将 JSON 换成 PostgreSQL？

因为它的 JSON 并不是简单保存几条记录。

我检查了 `api/server.js`，其中：

- `GET /api/data` 读取当前用户的完整数据。
- `GET /api/data/rev` 查询数据修订版本。
- `PUT /api/data` 保存训练数据。
- 发生版本冲突时，服务器返回 HTTP 409，并提供用于合并的数据。

前端通过 `useStore.js` 中的同步逻辑处理多设备修改。

如果直接改成普通的数据库 CRUD，很容易破坏现有的离线同步和冲突解决机制。

这也正是一个值得学习的工程设计。

建议先将数据库用于新增模块。未来需要迁移核心数据时，再设计兼容原有修订号和冲突处理协议的数据库存储层，并进行完整的数据迁移、回滚及同步测试。

相关代码：

- [服务端状态管理](https://github.com/DuarteSantos8/openGym/blob/main/api/server.js)
- [前端数据同步](https://github.com/DuarteSantos8/openGym/blob/main/frontend/src/store/useStore.js)
- [OpenAPI 接口规范](https://github.com/DuarteSantos8/openGym/blob/main/api/openapi.yaml)

## 四、SaaS 最关键的三个技术问题

### 1. 用户认证与数据隔离

现有系统支持多用户，但这不等于完成了 SaaS 所需的身份体系。

它采用的是 Passkey、签名会话以及可选的密码登录。

需要特别注意：现有密码登录默认关闭，电子邮箱虽然可以用作登录标识，但系统不负责发送验证或找回邮件，密码重置主要依赖管理员生成的一次性代码。

第一批测试用户可以沿用现有认证。

正式开放注册之前，建议补齐邮箱验证、账户恢复、用户协议、隐私告知和账户注销流程。

权限方面，至少测试这些场景：

- 用户 A 不能读取用户 B 的训练数据。
- 用户 A 不能通过修改请求参数访问 B 的 AI 报告。
- 普通用户无法调用管理接口。
- 退出登录后，受保护接口不能继续访问。
- 管理员操作具备审计记录。

以后考虑健身房业务时，再增加组织、教练、学员以及组织级数据权限。

**第一版不要提前开发复杂的 B2B 多租户系统。**

### 2. AI 调用成本

原项目的 AI Coach 已经具备管理员配置模型提供商的机制，默认配置还有每个用户每日 10 次的请求限制；实例级每日限制默认为不设上限。

但现有配额不能直接等同于商业 SaaS 的成本控制体系。

尤其是我在 `api/coach/routes.js` 中发现，**按用户分别配置 AI 提供商凭据的完整接口仍有尚未实现的部分**。

对我们的 SaaS 来说，我更建议初期由平台统一管理 API 密钥，用户不需要自行填写密钥。

新增的成本控制应包括：

- 每个用户每日、每月请求配额。
- 单次请求 Token 上限。
- 服务端记录实际模型用量和费用。
- 对重复报告使用缓存。
- 对高频请求做限流。
- 达到预算上限时停止生成付费报告。

成本计算可以采用：

`AI 成本 = 输入 Token 费用 + 输出 Token 费用 + 其他模型相关费用`

先用真实测试数据测量每份报告的平均成本，再决定免费额度和未来订阅价格。

### 3. AI 的准确性与安全性

我建议采用：

**确定性分析引擎 + 大模型解释 + 规则校验 + 用户确认。**

例如：

Python 根据训练历史算出：

```json
{
  "exercise": "Seated Row",
  "previous_weight_lb": 50,
  "current_weight_lb": 60,
  "change_percent": 20,
  "observation": "load_increased"
}
```

然后将经过校验的分析结果交给 AI。

AI 负责解释数据，不负责随意修改历史记录。

如果 AI 提出调整训练计划，需要进行格式校验、训练约束校验，并让用户确认。

原项目已经有一套 AI 修改操作白名单及校验机制，我们应该优先复用相关设计。

另外，肌肉恢复状态只能作为估计，不能作为医疗判断；对于疼痛、受伤等问题，系统需要明确自己的适用范围。

## 五、自动化测试与工程质量方案

这部分非常适合发挥你之前的测试开发经验。

openGym 并不是一个缺少测试的项目，它已经包含：

- 前端 Vitest 单元测试。
- Node.js 后端接口测试。
- AI Coach 校验测试。
- MCP 测试。
- GitHub Actions 自动化构建及测试。
- Docker 镜像构建与启动检查。

源码可以查看：

[`.github/workflows/test.yml`](https://github.com/DuarteSantos8/openGym/blob/main/.github/workflows/test.yml)

所以，我们不应该再从零搭建一套重复的测试框架。

我建议重点补充 **Python 服务测试、H5 端到端测试、SaaS 安全测试、AI 质量评估**。

| 测试类型 | 技术 | 主要测试内容 |
|---|---|---|
| 前端单元测试 | Vitest | React 组件、数据展示 |
| 后端单元测试 | pytest | 训练指标计算 |
| API 自动化 | pytest + httpx | FastAPI 接口、参数校验 |
| H5 自动化 | Playwright | 注册、登录、训练记录、查看报告 |
| 安全测试 | pytest | 越权访问、用户数据隔离 |
| AI 质量测试 | pytest + 固定数据集 | 幻觉、计算错误、不合理建议 |
| 并发测试 | Locust | 多用户访问、训练数据同步 |
| CI/CD | GitHub Actions | 自动执行测试、构建、部署 |

### 建议设计一个完整的 E2E 测试

```text
用户注册
    ↓
用户登录
    ↓
创建训练计划
    ↓
开始训练
    ↓
完成4组训练
    ↓
保存训练记录
    ↓
查看训练历史
    ↓
生成AI训练报告
    ↓
核对报告数据
    ↓
退出登录
```

这个流程同时覆盖前端、后端、数据同步、数据分析和 AI。

它可以成为你项目简历中的重要技术亮点。

特别要测试用户同时在手机和电脑修改训练记录的情况，不能因为引入新功能而破坏原有的同步机制。

## 六、开源许可证与商业化风险

这部分我认为应当在开发初期处理，而不是等到准备收费时再解决。

### 风险一：AGPL-3.0

openGym 的自有代码采用 AGPL-3.0-or-later。

你可以：

- Fork 项目。
- 修改代码。
- 自行部署。
- 向用户收取服务费用。

但如果你修改了 AGPL 程序并通过网络向用户提供服务，通常需要按照许可证要求向这些用户提供相应源代码。

这并不禁止 SaaS 商业化，但会限制闭源商业模式。

如果未来你希望把核心技术完全闭源，那么需要提前考虑独立实现、取得额外授权或重新设计代码组成方式。

### 风险二：健身动作动画版权

这个风险比我最初预计的更明确。

我查看了仓库中的：

[NOTICE.md](https://github.com/DuarteSantos8/openGym/blob/main/NOTICE.md)

其中明确说明：

**项目包含的健身动作图片和动画由 Gym visual 授权给 openGym，并不属于 AGPL 代码许可证的一部分。**

对于商业 Fork，需要取得自己的素材授权。

而且这些素材还被明确禁止用于训练、提示或输入 AI 系统。

因此，开发时应当采取以下策略：

| 阶段 | 素材方案 |
|---|---|
| 本地学习、非商业原型 | 按原项目许可和说明使用 |
| 公开商业化测试 | 提前解决素材授权 |
| 正式商业运营 | 使用取得商业许可的素材或自主制作的素材 |

**即使软件代码完全开源，也不代表其中所有图片和动画都可以自由商用。**

如果准备长期经营产品，我更倾向于逐步建立自己拥有合法使用权的动作素材库。

## 七、建议的 10 周开发计划

我把任务拆成四个阶段。

### 第一阶段：熟悉并稳定运行原项目（第 1–2 周）

**目标：完成技术调研，形成稳定的二次开发基线。**

| 任务 | 验收标准 |
|---|---|
| Fork openGym | 拥有自己的代码仓库 |
| 固定上游版本 | 基于 v1.4.1 等明确的版本开发 |
| Docker 本地部署 | MacBook 可以正常访问 |
| 熟悉 React 前端 | 能独立修改页面并运行 |
| 熟悉 Node API | 能定位训练记录接口 |
| 分析数据同步 | 理解版本冲突和数据合并 |
| 执行原有测试 | 建立基线测试报告 |
| 验证 AI Coach | 可以使用测试模型生成结果 |

第一阶段还应该记录原项目本身的问题，避免把上游缺陷误认为自己开发引入的缺陷。

我建议这个阶段先不要改动核心数据结构。

**第一阶段交付成果：**

一个可以运行、可以调试、可以部署，并且已经建立自动化测试基线的项目。

### 第二阶段：开发训练分析功能（第 3–5 周）

这是你独立开发能力的主要展示部分。

建议重点开发：

**基于 Python 的训练数据分析服务。**

例如：

```text
用户训练记录
     │
     ▼
  数据读取
     │
     ▼
  数据清洗
     │
     ▼
  指标计算
     │
     ├── 每周训练量
     ├── 力量变化
     ├── 计划完成率
     └── 训练频率
     │
     ▼
  PostgreSQL
     │
     ▼
  FastAPI
     │
     ▼
 React 数据可视化
```

建议先支持三个统计页面：

| 页面 | 功能 |
|---|---|
| 训练概览 | 最近 7 天、30 天训练情况 |
| 动作趋势 | 指定动作的重量、次数变化 |
| 训练分析 | 训练计划完成情况及变化趋势 |

这个阶段还需要完成 Python 单元测试、API 自动化测试和至少一组有明确预期结果的统计测试数据。

**验收标准：**

使用一组固定的四周训练记录，能够准确计算训练次数、各动作训练量和计划完成率。

用户修改或删除历史训练记录后，分析结果能够正确更新，不出现重复统计。

### 第三阶段：开发 AI 分析功能（第 6–7 周）

这部分可以继续利用 openGym 已有的 AI Coach。

我建议新增一个独立的：

**AI 训练分析报告页面。**

用户点击“生成训练报告”，系统完成：

```text
用户点击生成报告
        │
        ▼
检查用户权限与配额
        │
        ▼
读取最近训练数据
        │
        ▼
计算确定性指标
        │
        ▼
生成AI分析请求
        │
        ▼
调用大模型
        │
        ▼
校验返回结果
        │
        ▼
保存报告
        │
        ▼
展示报告与数据依据
```

报告可以包含：

- 本周训练总结。
- 最近训练变化。
- 值得关注的问题。
- 下周训练建议。
- 建议所依据的具体数据。

关键验收标准是：

**AI 不能编造不存在的训练数据。**

对于固定测试数据，报告引用的重量、次数、日期和变化比例必须与程序计算结果一致。

如果模型输出错误、超时或者消耗超出额度，系统也需要提供明确的失败提示。

### 第四阶段：上线与真实用户验证（第 8–10 周）

这个阶段不需要立即收钱。

主要工作：

| 任务 | 目标 |
|---|---|
| 云服务器部署 | 支持 HTTPS 访问 |
| 手机 H5 适配 | iPhone、Android 正常使用 |
| 用户数据隔离 | 无跨用户访问问题 |
| 数据备份 | 能完成备份和恢复演练 |
| 使用监控 | 能发现接口异常、AI 失败 |
| 邀请测试用户 | 首批 10–20 名 |
| 收集反馈 | 找到真实使用障碍 |
| 分析使用行为 | 判断用户是否愿意持续使用 |

需要注意，**10 周只是技术开发与首轮试用计划，不等于能在第 10 周完成四周留存验证**。如果用户在第 9 周才加入，就需要继续观察四周。

商业化之前，我们至少需要了解：

1. 用户是否能够持续记录训练。
2. 用户是否愿意主动查看 AI 分析。
3. AI 报告是否真正改变用户的训练行为。
4. 用户是否愿意付费获得这些功能。

如果发现用户根本不关心 AI 分析，而更关心训练记录是否方便，那就应该调整产品方向。

## 十、我们现在应该从哪里开始？

我建议下一步不要急着开发 FastAPI，而是先完成 **openGym 的本地运行和基础功能验证**。

你目前使用的是 MacBook Air M1，可以通过 Docker Desktop 部署。项目本身支持 ARM64。

另外，建议以正式 Release 作为开发起点，而不是直接长期跟随 `main` 分支。因为上游仍在快速迭代，我们不希望自己的修改被上游变化不断打断。

具体的第一步就是：

**Fork 仓库 → 固定版本 → Docker 本地部署 → 跑通训练记录和 AI Coach → 建立测试基线。**

完成后，再开始分析训练数据结构并设计 FastAPI 服务。

### 最终技术路线

**React H5 + openGym 原有 Node.js API + FastAPI 数据分析 + PostgreSQL + AI 模型 + Docker。**

但这些技术不需要一次性全部引入。

对你来说，这个项目最大的价值是能够让你逐步掌握：

**从需求分析、业务开发、接口设计、自动化测试，到 AI 集成、部署上线和真实产品运营的完整流程。**

同时保留商业化的可能性。

我建议就按照这个方案推进，**第一步先把 openGym 在你的 Mac 上部署起来，并完整体验它已有的功能**。这能帮助我们在正式二次开发前，进一步缩小真正需要自己开发的范围。
